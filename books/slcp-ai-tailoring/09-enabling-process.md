第3章から第8章の設計は、個人とチームの単位で回るものであった。本章では、それを組織の仕組みとして回す設計を示す。対象は、ISO/IEC 12207の組織的プロジェクトイネーブリングプロセスである。個人の工夫を消える形にせず、組織の資産として残し、他の案件に活かすことが、本章の主題である。

### 9.1 対象のプロセス

組織的プロジェクトイネーブリングプロセスは、ライフサイクルモデルの管理、インフラストラクチャの管理、ポートフォリオの管理、人的資源の管理、品質の管理、知識の管理の六つからなる。本稿の設計との対応は、次のとおりである。

- ライフサイクルモデルの管理: テーラリングの型そのものを、組織の資産として管理する
- インフラストラクチャの管理: 使ってよい道具と、セキュリティの境界を定める基盤を用意する
- ポートフォリオの管理: どの案件に適用するかを選択し、投資の評価軸を持つ
- 人的資源の管理: 前提スキルから目指すスキルへの育成を設計する
- 品質の管理: ゲートと検証の仕組みを、案件を越えて維持する
- 知識の管理: 型と事例と判断の記録を蓄積し、再利用できる形にする

### 9.2 型の組織資産化

テーラリングの成果物（テンプレート、指示ファイル、レビューの観点、事例）は、案件の中で作られ、組織の資産として残す。資産化とは、置き場所と形を定めて、作った本人以外が使える状態にすることである。

展開の姿勢も、仕組みの一部である。型と記録を静かに残し、採用するかどうかは各現場に委ねる。押し付けられた型は形だけが残り、判断の層が育たない。使った現場の事例が知識の管理へ戻ることで、資産は育つ。

### 9.3 人的資源の管理と育成

育成の方針は三つである。

第一に、土台は標準知識に置く。第6章の前提スキルがそれであり、現段階の棚卸しはIPAのシラバスが与える。資格の取得は手段の一つであり、目的は共通の物差しを持つことである。

第二に、段階を明示する。前提スキルを全員の共通の到達点とし、その上に第7章の目指すスキル（判断と振る舞いの層）を伸ばす段として設計する。

第三に、育成の成果は価値の成果で測る。受講時間や資格の数といった活動量ではなく、レビューでの盲点の検出、手戻りの削減、意思決定への寄与で測る。

業務側の育成も、この章の対象である。第6章で前提として置いた業務側のAIリテラシーの中身は、目的を言葉にする力、AIの出力を吟味する力、機密と公開の線引きを引く力であり、業務部門側の教育の項目として設計する。

この方針は、現場に作れる人を送り込む方式（フォワード・デプロイド・エンジニア）の成果主義と同型である。成功を、技術的な複雑さや成果物の量ではなく、現場の成果で測る点が共通する。次の形は、作れる人を現場へ送ることから、現場の人が作れるようになることへの移行であり、運ぶ対象が人から能力へ移る。

### 9.4 計測の置き場所

本章の計測は、仕組み化への投資判断と、ポートフォリオの評価のために置く。開発そのものの効率の計測は第10章の対象であり、役割を分ける。

投資対効果の考え方は単純である。投資は、型の整備、教育、基盤の用意にかかる費用と時間である。回収は、手戻りの削減、案件の立ち上がり期間の短縮、判断の質の向上として現れる。各プロセスのKPIは、活動量ではなく、価値の成果に連動させて取る。

| プロセス          | KPIの取り方の例                       |
| ------------- | ------------------------------- |
| ライフサイクルモデルの管理 | 型を適用した案件における手戻りの発生率             |
| インフラストラクチャの管理 | 境界の内側で安全に使える道具の整備状況、境界を越えた利用の件数 |
| ポートフォリオの管理    | 適用案件の事業成果への寄与、投資に対する回収の期間       |
| 人的資源の管理       | レビューでの盲点検出の実績、判断を担える人材の広がり      |
| 品質の管理         | 後工程へ流出した欠陥の件数と、その発生段階の内訳        |
| 知識の管理         | 型と事例の再利用の回数、再利用した案件の立ち上がり期間     |

KPIはどのプロセスに次の投資を置くかを判断するための数字であり、判断の材料として経営の層へ上がる。監視のための数字ではない。

公の側にも、同じ構造の動きがある。デジタル庁は、政府職員が生成AIを安全に使える基盤として、ガバメントAI「源内」を内製し、全府省庁への展開を進めている。源内が用意するのはAIモデルそのものではなく、複数のモデルとアプリケーションを安全な境界の内側で使うための器である。あわせて公表された「源内基準」は、利用者・管理者・開発者のそれぞれに守るべき事項を定めており、本稿の言葉で言えば、制約構造を行政の側で定めたものにあたる。

器が公の側から用意されても、その上での仕事の設計は残る。どのプロセスにどの制約を置き、判断をどこに残すかは、使う組織ごとのテーラリングである。共通フレームがIPAから、源内がデジタル庁から生まれたように、物差しと基盤は公の側が用意し、使い方の設計は現場が担う。本稿の実践は、その現場側の設計の一例である。
